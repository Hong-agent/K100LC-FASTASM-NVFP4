## 2026-09-29 · NVFP4 扩面到全部线性层：A/B 结论

`tools/nvfp4_quant.py` 把 checkpoint 里那批 **FP8（逐通道）** 的线性层
（自注意力 q/k/v/o、线性注意力 in_proj_qkv/in_proj_z/out_proj、lm_head、
第 56~63 层 MLP，共 233 个张量）按 **与 MLP 完全相同的 NVFP4 规格**重量化，
运行时走同一批 `k_nvfp4_*` 内核。两套权重都打出来对拍（都是本机 K100_LC，
`bash scripts/bench.sh` 的默认档：8192 token 预填充 / 500 token 生成）：

| 指标 | 只有 MLP 是 NVFP4（RT4 int4 跑其余层） | 全部线性层 NVFP4 | 变化 |
|---|---|---|---|
| P_prefill（tok/s） | **295.3** | **251.3** | **−14.9%** |
| D_mtp3（贪心 tok/s） | 27.2 | 29.0 | +6.6% |
| A_mtp（接受 token/轮） | 0.808（47.5%） | 1.058（54.2%） | + |
| D_nomtp（tok/s） | 21.4 | 21.2 | −0.9% |
| 单矩阵 GEMV（lm_head 248320x5120） | 0.904 ms / 703 GB/s | 1.094 ms / 581 GB/s | −17% |
| model.rp4 体积 | 15.765 GB | 16.263 GB | +3.2% |

结论：**权重精度更好**（每 16 个 k 一个 E4M3 尺度，实测相对 RMS ≈ 9.5%，
对照 RT4 int4/128 的 ≈ 12%；贪心输出与 int4 版语义一致 —— 前 64 个 token
相同 57.8%，随后只是措辞不同），**解码基本不变，但预填充慢 15%**。

原因：预填充是算力受限，RT4 的 W4A8 路径虽然要跑两遍 int4 GEMM，但每一遍
都比 `nvfp4_gemm_kernel`（BM=64/BN=64，每 16 个 k 折一次浮点尺度）快一倍以上，
两遍加起来仍然赢；解码侧（GEMV，单遍）NVFP4 也只是略慢，因为多出来的是
FP4→int8 解码 + 每 16 一个尺度那一层的开销。

要把它变成净收益，得先优化 `nvfp4_gemm_kernel`（更大 BM 复用权重、把每 16
一个尺度那层折叠掉）—— 那属于内核侧改动，而内核机器码来自 `kernels/asm/**/*.s`。

想回到「预填充优先」的打包方式：`NVFP4_ALL=0 bash scripts/pack_weights.sh`。
## 2026-09-29 · nvfp4_gemm_kernel 为什么慢：反汇编 + 微基准

用新加的 `GEMMBENCH <steps> [M]`（引擎 op，见 `src/model.cpp`）在**同一台机器、
同一个形状**上直接对比两种 GEMM 实现（`.rp4` 决定一个线性层走 NVFP4 还是 RT4 的
W4A8 两遍 int4 + add），M 取 512（= 运行时预填充的 `CHUNK`）：

| 形状 | NVFP4 单遍 | RT4 int4 W4A8 两遍 | 比值 |
|---|---|---|---|
| q_proj `[12288x5120]` | 9.8 TMAC/s | **17.4 TMAC/s** | 0.56× |
| k_proj `[1024x5120]` | 2.2 TMAC/s | 5.9 TMAC/s | 0.37× |

两个硬上限（`k100lc资料/K100LC-gfx926-性能数据.csv`，本卡实测）：
`v_dot8_i32_i4` = 75.6 TMAC/s（8 MAC/指令）、`v_dot4_i32_i8` = 37.8 TMAC/s（4 MAC/指令），
两者都是 9.45 G-inst/s 下发率。也就是说：

* int4 两遍 = 2×MAC、每条指令 8 个 → 指令数和 NVFP4 单遍（每条指令 4 个）**完全一样**，
  所以差异只能来自指令之外的开销；
* NVFP4 单遍实测 9.8 TMAC/s ≈ 上限的 **26%**，int4 两遍 ≈ 上限的 46%。

`kernels/asm/k_nvfp4/002__…nvfp4_gemm_kernel…s`（1055 行，即内核的机器码来源）的
指令统计（一个 K-tile、每线程）：

| 成分 | 条数 | 占比 |
|---|---|---|
| `v_dot4_i32_i8`（真正干活） | 256 | 35% |
| 尺度折叠：`v_cvt_f32_i32` 64 + `v_fmac_f32` 64 + `v_mul_f32` 67 | 195 | **27%** |
| 行/列边界判定：`s_cbranch_execz` 31 + `s_and_saveexec_b64` 23 + `s_or_b64` 29 | 83 | 11% |
| `s_waitcnt`（等访存/同步） | 51 | — |
| `ds_read_b128` 32 + `ds_read2_b32` 16 + 其余地址运算 | ~150 | 21% |

对照 int4 的 `gemm_w4a4`：BM=128（NVFP4 是 64）、双缓冲流水（`BUF=2`，先把下一块全局读
进寄存器、跑完点积再写 shared —— NVFP4 是「读→解码→写 shared→同步→点积→同步」全串行）、
**每 128 个 k 折一次尺度**（NVFP4 每 16 个 k 折一次，所以折叠指令是它的 8 倍）、
并且 `v_dot8_i32_i4` 直接吃打包 int4，**不需要解码**（NVFP4 要 FP4→int8）。

结论与优化目标（都在内核机器码侧，本项目没有 GPU 编译器，只能手工改 `.s`）：

1. **去掉边界判定**（-11%）：我们的形状 M/N 都是 64 的整数倍（LM head 248320 也是），
   加一个「整除就调无守卫版本」的分支即可；需要一份去掉谓词的内核副本。
2. **软件流水/双缓冲**（-10~20%）：照 `gemm_w4a4` 的写法把下一 K-tile 的全局读提前。
3. **BM 从 64 提到 128**：权重解码/shared 写入摊到两倍的行上。
4. 尺度折叠（27%）**改不掉** —— 除非把权重尺度从每 16 改成每 128（那就退化成 int4 的
   精度，与「和 MLP 规格一致」冲突）。

另外记一个**已知限制**：NVFP4 GEMM 在 M ≥ 1024 时会触发非法地址访问（M=128/256/512
正常）。运行时预填充的 `CHUNK=512`，所以模型跑不到；`GEMMBENCH` 默认只测这三档。
