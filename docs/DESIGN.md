# 设计：在 K100_LC 上**直接**跑 NVFP4

> **状态（2026-09-30）：这条路已降级为备用选项**，项目默认跑 int4
> （`RedHatAI/Qwen3.8-27B-INT4` → RT4 W4A8）。实测 NVFP4 全量直跑预填充 −14.9%、
> GEMV −17%、体积 +3.2%，精度虽好（RMS ≈9.5%）但换不来性能，详见
> [BENCHLOG.md](BENCHLOG.md)。本文档作为「为什么可以无损、代价在哪」的设计记录保留。

目标：拿 `unsloth/Qwen3.8-27B-NVFP4` 这种压缩好的 checkpoint，**不做任何转换、
不做任何重量化**，直接在 gfx926 上执行。本文说清楚三件事：
为什么可以无损、为什么必须走 int8 通路、以及每部分的实测性能与代价。

---

## 1. NVFP4 的两种精度

模型里 NVFP4 只覆盖 56 层 MLP 的 `gate/up/down_proj`（168 个张量，14.97B 参数，
7.49 GB 打包 + 0.94 GB 尺度）。其余（注意力投影、线性注意力、`lm_head`、
第 56~63 层的 MLP）是 **FP8 per-channel**，不在本项目范围内——本项目的对象就是
这 168 个 NVFP4 张量，它们占了整份权重里最大的一块。

格式（compressed-tensors `nvfp4-pack-quantized`，逐字段核对过，见
[NVFP4-FORMAT.md](NVFP4-FORMAT.md)）：

```
weight_packed        U8   [N, K/2]    两个 E2M1 码一个字节，**偶数 k 在低半字节**
weight_scale         E4M3 [N, K/16]   每 16 个 k 一个块尺度
weight_global_scale  F32  [1]         逐张量

w[n,k] = e2m1(code) * e4m3(weight_scale[n, k/16]) / weight_global_scale
```

## 2. 为什么 FP4 → int8 是**无损**的

E2M1 的 16 个码只有 8 个幅值 0、0.5、1、1.5、2、3、4、6。把它们**乘 2**：

```
2 x E2M1 = { 0, ±1, ±2, ±3, ±4, ±6, ±8, ±12 }
```

**全部落在 [-12, 12] 的整数上，而 int8 装得下。** 于是

```
w[n,k] = I(code) * S[n,k/16] / 2          I = 2 x E2M1，是精确整数
        = I(code) * (e4m3(weight_scale) / weight_global_scale) / 2
```

右边那个括号是**逐块浮点尺度**，与码无关；整数部分 `I` 由码唯一决定，**没有任何
舍入**。也就是说：

> FP4 → int8 只差一个整块的浮点因子，权重侧的量化误差是 **0**。

这一点和「离线转 int4」有本质区别（见 §5）。

## 3. 算法：整数点积 + 逐块浮点尺度

设激活也按 **同样的 16 块**量化到 int8：

```
a[m,k] = qa[m,k] * sa[m, k/16]           qa 是 int8
```

那么

```
y[m,n] = Σ_k w[n,k] a[m,k]
       = Σ_g  (e4m3(ws[n,g]) / gscale / 2) * sa[m,g] * ( Σ_{k∈g} I[n,k] * qa[m,k] )
                 └──────────── 逐块浮点 ────────────┘   └──── 精确整数点积 ────┘
```

整数和用 `v_dot4_i32_i8` 算（|I| ≤ 12，|qa| ≤ 127，16 项的和最大 24384，int32 绰绰有余），
每跨过 16 个 k 就把整数和乘上两个浮点尺度折进 f32 累加器。

**误差只来自激活量化**（每 16 个 k 一个 int8 尺度），权重那侧是零误差。
对照：模型自带的 `input_global_scale` 说明参考实现也是按 16 块量化激活的，
我们用 int8 而不是 FP4，所以激活侧还比参考实现更准。

## 4. FP4 → int8 的解码怎么做得便宜

一个 32 位打包字 = 4 字节 = 8 个 FP4 码。要让 `v_dot4_i32_i8` 能用，需要两组
「4 个 int8」：

```
W_e = [I(k0), I(k2), I(k4), I(k6)]     W_o = [I(k1), I(k3), I(k5), I(k7)]
```

码在字节里是 `(code>>3)=符号, code&7=幅值索引`，所以一次 `v_perm_b32` 就能当
8 字节 LUT 用（正表 4 项 + 负表 4 项，gfx926 的两个操作数方向要按实测来摆），
再用一次 `v_perm_b32` 造逐字节 `0x00/0xFF` 符号掩码，三次异或选择出结果：

```
idx  = x & 0x07070707          sgn  = (x>>3) & 0x01010101        (偶数码)
pos  = v_perm(P_A, P_B, idx)   neg  = v_perm(N_A, N_B, idx)
mask = v_perm(0,   0x0000FF00, sgn)
W_e  = pos ^ ((pos ^ neg) & mask)
```

一个打包字解成 `W_e/W_o` 大约 **19 条指令**（8 个元素），再加 2 条 `v_dot4_i32_i8`。
折算 **≈ 2.6 条指令/元素**。

这个代价在两种负载里的意义完全不同（见 §6）。

## 5. 中心权衡：无损 vs 快一倍

`v_dot8_i32_i4` 的 nibble 是**有符号 −8..7**，而 `I` 有 **25 个取值**，
`±8` 与 `±12` 落在范围外。想要 `c·value` 对 16 个码都是 [-8,7] 的整数，
需要同时满足 `0.5c` 和 `6c` 是整数且 ≤7 —— 不可能。

> **结论：在 gfx926 上，无损跑 NVFP4 用不了 int4 通路，天花板是 int8 的 37.8 TMAC/s。**
> 要 75.1 TMAC/s 就必须离线二次量化成 int4，那是有损的（`K100LC-RT4` 那条路线）。

| 路线 | 权重 | 通路 | 峰值 | 权重精度 | 需要离线转换 |
|---|---|---|---|---|---|
| **本项目**（NVFP4 直跑） | FP4 原位 | `v_dot4_i32_i8` | **37.8 TMAC/s** | **无损** | 不需要 |
| 离线转 int4 | int4 | `v_dot8_i32_i4` | 75.1 TMAC/s | 二次量化，实测 relerr 逐个记录 | 需要（4.5 分钟 / 13.9GB） |

两条路线不冲突：**精度优先或不想动 checkpoint 就用本项目；预填充要冲极限就用
离线 int4。** 本项目的价值在于证明了「不动权重也能跑，而且精度更好」。

## 6. 两种负载，两个内核

### 6.1 解码（GEMV，M=1）——访存受限

每元素只有 0.5 字节权重，804 GB/s 下 1.6e12 元素/s；ALU 只有 9.75e12 lane-ops/s，
所以**每元素预算 6.1 条指令**。解码只要 2.6 条 —— **白送**。

| 版本 | 载入宽度 | 等效带宽 | 8.42GB 一遍 | 折算 |
|---|---|---|---|---|
| 标量版（每 lane 一个 16 分块） | 64 位 | 476 GB/s | 17.68 ms | 56.5 token/s |
| **宽载版**（每 lane 两个 16 分块） | 128 位 | **560 GB/s** | **15.0 ms** | **66.5 token/s** |
| 同尺寸纯读上限（实测） | 64 位 | ~680 GB/s | 12.4 ms | — |

宽载版到纯读上限的 **82%**，已经是访存受限。`kernels/nvfp4_gemv.hip` 里有
NROW / 线程数 / 载入宽度的完整消融。

> 这 65.4 token/s 只是**这 8.42 GB NVFP4 权重**的限制；整模型还要加 FP8 的
> 11.5GB 权重与 KV，所以端到端上限还要再除以约 2.4。这个数字的意义是给出
> 「NVFP4 这部分能跑多快」的硬上界。

### 6.2 预填充（GEMM）——算力受限

这里每元素 2.6 条解码指令会直接吃掉点积吞吐，所以必须**把权重协作解码进
shared memory 一次，再让 BM 行激活复用**（摊销掉解码）。

实测 `TM=TN=4, BK=64`：

| 形状 | 用途 | 实测 | 占 int8 峰值 |
|---|---|---|---|
| M=1000 N=17408 K=5120 | gate/up_proj | **12.79 TMAC/s** | 33.8% |
| M=4096 N=17408 K=5120 | 长预填充 | 13.29 TMAC/s | 35.2% |
| M=1000 N=5120 K=17408 | down_proj | 10.25 TMAC/s | 27.1% |

### 6.3 一个真实踩到的坑：shared memory bank 冲突

第一版把权重按 `[行][dword]` 存进 shared（行距 32B）。结果 16 个线程的地址
间隔恰好是 128B 的整数倍，**全部落在同一个 bank**，16 路冲突，只有 3.57 TMAC/s。
改成 `[dword][行]` 转置存法之后 **13.07 TMAC/s，快 3.66 倍**。
（细节在 `kernels/nvfp4_gemm.hip` 的注释里。）

## 7. 框架

```
tools/nvfp4_layout.py   扫 safetensors 头，产出「张量 -> 文件偏移」清单
        |
        v
src/nvfp4_run.hip       mmap 原始权重 -> 显存 -> 跑内核 -> 与 float64 参考对照
        |
        +-- kernels/nvfp4_gemv_kernel.h   解码 GEMV（标量版 + 宽载版）
        +-- kernels/nvfp4_gemm.hip        预填充 GEMM
        +-- include/nvfp4/nvfp4_decode.h  FP4->int8 / E4M3->f32 原语（与主机参考同一张表）
```

运行时**不做任何数据变换**：`weight_packed` 和 `weight_scale` 原样从 mmap 拷到显存，
内核直接按 checkpoint 的 `[N, K/2]` / `[N, K/16]` 布局寻址。清单里的偏移是
文件内绝对偏移，所以连解析 JSON 都不需要在 C++ 里做。

## 8. 精度实测（真实权重）

`src/nvfp4_run.hip --check` 对每个张量抽行，用**直接从 mmap 字节算出来的 float64**
做对照：

```
168 个张量，最坏相对误差 3.99e-07      (GEMV，含 17408 长的行内 float32 累加)
GEMM 抽查最坏相对误差 9.6e-05          (K=5120 的 float32 逐块累加，属正常量级)
```

也就是**内核与「无误差参考」的差就是 float32 自身的舍入**，没有别的误差来源。
