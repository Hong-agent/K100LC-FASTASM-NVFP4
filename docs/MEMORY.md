# 权重能不能不载入显存/内存，直接从硬盘跑？

结论先说：

* **内存：现在就已经是「不载入」了**。运行时是 mmap，22.5GB 的模型跑在
  7.5GB 物理内存的机器上，系统内存稳定在 ~2GB。
* **显存：不可能完全不载入**，这是独立 DCU 的硬限制；但**可以只驻留一层**，
  代价是慢约 600~900 倍。

## 1. 三条通路的实测带宽（本机 K100_LC + 本机磁盘）

`bench/probe_zerocopy.cpp` 一次测完：

| 通路 | 实测 | 说明 |
|---|---|---|
| 磁盘顺序读 | **0.91 GB/s** | `pread` 4GB，32MB 块 |
| 主机内存到 GPU 直读（零拷贝） | **6.6 GB/s** | `hipHostMallocMapped` + `hipHostGetDevicePointer`，本机**支持** |
| 显存读 | **452.9 GB/s** | 简单网格跨步；优化过的访存模式可到 680~800 |

零拷贝这条是意外收获：**gfx926 支持内核直接读主机内存**，所以「权重只放内存、
不进显存」是可行的，只要内存装得下。

## 2. 为什么「完全不载入显存」不可能

这是独立显卡：SM 的乘法器只能从显存取操作数，SSD 和 ALU 之间没有通路。
权重在**被算到的那一刻**必须在显存里。这是硬件事实，不是实现选择。

但「整份常驻」不是必须的。可以**逐层流式**：拷第 L 层的权重进一块复用缓冲，
算第 L 层，下一层复用同一块。显存占用从 22.3GB 降到约 1.5GB
（一层 MLP 的权重 + KV cache + 激活）。

## 3. 代价：解码会慢约 600~900 倍

解码是**权重带宽受限**的负载：每生成一个 token 就要把全部权重读一遍
（RT4 路径 13.9GB；只算 NVFP4 的 MLP 也有 8.4GB）。

| 权重放哪 | 每步读 13.9GB 需要 | 解码上限 |
|---|---|---|
| 显存 | 17 ms | **约 58 token/s** |
| 主机内存（零拷贝；需 ≥22.5GB 内存，本机只有 7.5GB） | 2.1 s | 约 0.5 token/s |
| 硬盘 | 15.3 s | **约 0.065 token/s** |

也就是说：改成硬盘流式之后，**一步还吐不出一个字**。对交互式对话没有意义；
只有在「模型比显存大、无论如何要跑起来」的场景才值得这么换。

## 4. 内存那块为什么本来就没问题

`RT4::load()` 用的是 `mmap(MAP_PRIVATE, PROT_READ)`：文件页是**只读、可回收**的，
内核随时能把它们丢掉，只有正在被 DMA 的那几百 MB 会短暂驻留。
实测跑对话时系统内存稳定在 1.9~2.1GB，和模型大小无关。

（真正吃内存的是别的东西：HIP 运行时、Python、tokenizer。不是权重。）

## 5. 已做：去掉重复的那份权重

混合模式下原来显存里**同时躺着两份 MLP 权重**：RT4 的 int4 重量化版 7.5 GB
（`rt.upload()` 整份拷贝带进去的，一个字节都不会被用到）+ NVFP4 直跑版 8.4 GB。

现在改成**紧凑布局**：上传时把这些被取代的张量整段跳过，只给真正要用的张量分配
显存（每个张量记一个 `d_delta`，`qptr`/`sptr` 加上它就能拿到正确地址）。

实测（同一 prompt、贪心解码）：

| | 老布局 | 紧凑布局 |
|---|---|---|
| 显存峰值 | **25.67 GB** | **18.48 GB** |
| RT4 那部分 | 13.91 GB（读满） | 6.19 GB（跳过 7.72 GB 的读与拷） |

## 6. 已做：加载与第一次请求重叠

原来 `Model::init()` 同步把 22GB 读进来才返回，服务要 21 秒后才可用。
现在：

* 权重按**前向顺序**分成 67 组（embedding / 第 il 层 / 其余全局权重），
  登记进后台加载线程（`src/prefetch.h`）；
* 加载线程用 page-locked 缓冲 + `pread` + 异步入队，把**磁盘读和 PCIe 拷贝叠起来**；
* 初始化立刻返回，服务马上可用；`forward()` 在用到第 il 层之前
  `hipStreamWaitEvent` 等这一组，GPU 一边算第 il 层，加载线程一边搬第 il+1 层。

实测：

| | 同步加载 | 按层重叠 |
|---|---|---|
| 服务就绪 | 21.2 s | **2.8 s** |
| 首字延迟 | 21.2 s | 18.8 s |

（首字仍要等全部 64 层，这是解码必须读遍所有权重的性质决定的；重叠省掉的是
"必须等完才开始"的那段串行时间，以及服务可用性的 7.6 倍差距。）

两个踩过的坑，都写进注释了：

1. `hipStreamWaitEvent` 对**还没记录过**的事件是空操作 —— 只靠事件同步会静默地
   读到没加载完的权重（表现是模型输出变成 `the the the`）。必须先过一道主机侧计数器。
2. 两个来源（RT4 权重 + 原始 NVFP4 safetensors）是分别登记的，**必须全局按组排序**，
   否则后登记的那批永远轮不到加载。

开关：`RT_PREFETCH=0` 退回同步加载，`RT_COMPACT=0` 退回老布局（都只用于 A/B 排查）。

## 7. 已做：把要加载的权重拼成一个连续文件

原来运行时要从**两个文件**里按 851 + 336 个散落偏移去读（RT4 权重一个文件、
原始 NVFP4 safetensors 另一个）。`tools/nvfp4_pack.py` 把它们按**前向顺序**
拼成一个连续文件，于是「文件偏移 == 设备偏移 == 加载顺序」，加载退化成一次
顺序读 + 顺序拷，运行时也不用再算紧凑布局。

```
bash scripts/hybrid.sh pack      # 生成 build/packed.bin（14.61 GB，约 25 秒）
```

（运行时默认就会用它；`RT_PACKED=0` 可以关掉。）

### 真正的加速来自 O_DIRECT

拼成连续文件之后，顺手把读取改成 `O_DIRECT`，这一下才是关键：

| 同一块盘读同一个文件 | 实测 |
|---|---|
| `pread`（走页缓存） | **0.96 GB/s** |
| `dd iflag=direct`（O_DIRECT，32MB 块） | **3.1 GB/s** |
| 4 路并发 O_DIRECT | ~4 GB/s |

原因是这台机器**只有 7.5GB 内存，而文件 13GB** —— 走页缓存会被反复换出，
吞吐被拖到 1/3。绕开页缓存之后盘的真实能力才显出来。

### 三段加起来的效果

| 配置 | 服务就绪 | 首字延迟 |
|---|---|---|
| 散读 + 页缓存（最初） | 21.2 s | 21.2 s |
| 打包 + 页缓存 | 2.6 s | 17.0 s |
| **打包 + O_DIRECT** | **2.6 s** | **7.9 s** |

答案在每一档都核对过（`巴黎` / `北京`）。
