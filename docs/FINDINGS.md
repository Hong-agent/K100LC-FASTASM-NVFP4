# 探索记录：gfx926 上跑 NVFP4 的可行性与上限

本文是 `bench/probe_isa.cpp` 的实测结论汇总，所有数字都在本机
**K100_LC（gfx926，120 CU @1270MHz，sramecc+，无矩阵核心）** 上跑出来。

## 1. 这张卡的算力通路（复测）

| 指令 | 每指令 MAC | 实测峰值 |
|---|---|---|
| `v_dot4_i32_i8` | 4 | **37.8 TMAC/s** |
| `v_dot8_i32_i4` | 8 | **75.1 TMAC/s** |
| `v_dot2_i32_i16` | 2 | 18.9 TMAC/s |
| `v_dot2_f32_f16` | 2 | 16.8 TMAC/s |
| `v_pk_fma_f16` | 2 | 16.9 TMAC/s |

两条点积指令的**指令发射率是一样的**（≈9.5 T-inst/s），差别只在每指令 MAC 数。
所以「更快」等价于「每条指令塞进更多 MAC」——这正是 int4 通路比 int8 快一倍的原因。

## 2. 有符号/无符号语义（决定数据结构）

| 探针 | 输入 | 结果 | 结论 |
|---|---|---|---|
| `v_dot8_i32_i4` | nibble 1 × 0xF / 0x8 / 0x7 | −8 / −64 / 56 | **有符号 int4**（−8..7） |
| `v_dot4_i32_i8` | byte 1 × 0xFF | −4 | **有符号 int8**（−128..127） |
| `v_dot8_u32_u4` | 全 1 × 全 1 | 8 | **存在**，无符号 4bit |

`v_dot8_u32_u4` 存在这点很重要：它说明硬件有「无符号 4bit × 无符号 4bit」的乘法器，
但**没有**「无符号 4bit × 有符号 8bit」这种混合宽度的点积，所以无符号方案没法直接
和量化到 int8 的激活配对，不能用。

## 3. 没有 fp8 / fp4 转换硬件

```
v_cvt_f32_fp8 v0, v1   ->  error: instruction not supported on this GPU
v_cvt_f32_bf8 …        ->  同上
```

结论：**E4M3 块尺度只能靠位运算解**（本仓库用 `e4m3_to_f32()`，1 次 per 16 权重，
成本可忽略）。同时也说明这张卡不可能有原生 FP4 矩阵通路。

## 4. `v_perm_b32` 的实测语义（当 LUT 用的关键）

探针：`v_perm_b32 %0, %1, %2, %3`，`%1` 每字节 = 0x11..0x14，`%2` 每字节 = 0x21..0x24。

| index（4 字节都相同） | 结果 |
|---|---|
| 0 / 1 / 2 / 3 | 0x21 / 0x22 / 0x23 / 0x24 → **取第 2 个操作数的字节 0..3** |
| 4 / 5 / 6 / 7 | 0x11 / 0x12 / 0x13 / 0x14 → **取第 1 个操作数的字节 0..3** |
| 0x80 / 0xC0 / 0xFF / 0x88 | **0xFFFFFFFF** |

两点与常识不同，写内核时必须按实测来：

1. **操作数顺序是反的**：index 0..3 选的是**第二个**源寄存器的 4 个字节，
   4..7 选的是**第一个**。所以「表」要怎么放进两个寄存器要按这个来摆。
2. **index 字节 bit7 置位时输出 0xFF（不是 0x00）**。

这两条合起来正好给了我们一个**免费的逐字节符号掩码**：
把 `(code>>3)&1`（0/1）当 index，第 2 个源放 `0x0000FF00`
（字节 0 = 0x00，字节 1 = 0xFF），一次 `v_perm` 就得到 `0x00/0xFF` 的字节掩码。

## 5. 决定性结论：FP4 不可能无损塞进 int4

`v_dot8_i32_i4` 的 nibble 是**有符号 −8..7**。而 NVFP4 的 E2M1 码反量化后的
「权重量化步数」是

```
T = { 0, ±1, ±2, ±3, ±4, ±6, ±8, ±12 }        (即 2 × E2M1 的值)
```

共 **25 个不同取值**，`±8` 与 `±12` 都在 int4 范围外。想把 E2M1 线性映射进
有符号 int4，需要 `c·value` 对 16 个码都是 [−8,7] 内的整数，而 value 里同时有
0.5 和 6，`c·0.5` 与 `c·6` 不可能同为 ≤7 的整数。

### 由此得到本项目的中心结论

| 路线 | 权重位宽 | 通路 | 峰值 | 精度 |
|---|---|---|---|---|
| NVFP4 **直跑**（本项目） | int8（2×E2M1 精确整数） | `v_dot4_i32_i8` | **37.8 TMAC/s** | **权重无损** |
| 离线重量化成 int4 | int4 | `v_dot8_i32_i4` | 75.1 TMAC/s | 二次量化，有损 |

也就是说：**在 gfx926 上，无损地把 NVFP4 跑起来，算力上限正好是 int4 路线的一半**；
换来的是「不改一个权重、不需要离线转换、精度只由激活量化决定」。
RT4 项目走的是下面那条（离线转 int4），本项目走上面那条，两条并不冲突，可以按
「精度优先 / 速度优先」二选一，见 [DESIGN.md](DESIGN.md) §5。

## 6. 解码的代价

把 4 个 FP4 码经 2 次 `v_perm` + 选择解成 int8 再喂 `dot4_i32_i8`，
实测 **8.98 TMAC/s**，只有纯点积（32.7）的 1/3.6。折成「每元素指令数」：

```
FP4 权重带宽           0.5 B/元素
解码 + 点积 指令密度   ≈ 2.6 条/元素
可用指令预算           9.75e12 lane-ops/s ÷ 1.6e12 元素/s = 6.1 条/元素
```

**预算 6.1 条、实际 2.6 条** ⇒ 解码开销在**访存受限的解码（GEMV）里是白送的**，
因为那时候瓶颈是 804 GB/s 的显存而不是 ALU。
只有在**算力受限的预填充（GEMM）**里解码才会直接吃掉点积的速度，
所以 GEMM 必须把解码摊掉（协作解码进 shared memory 后再复用），见 DESIGN.md §4。

## 8. 由这些结论落地的内核（实测汇总）

探索的结论直接用在了两个内核上，完整数据见 [DESIGN.md](DESIGN.md) §6：

| 场景 | 内核 | 关键选择 | 实测 |
|---|---|---|---|
| 解码 GEMV（M=1） | `nvfp4_gemv` 宽载版 | 每 lane 两个 16 分块 + 128 位载入 | 551 GB/s（纯读上限约 680） |
| 预填充 GEMM | `nvfp4_gemm` | 协作解码进 shared；shared **转置**存 | 12.8~13.3 TMAC/s（int8 峰值 37.8 的 34~35%） |

两个额外踩坑，都写进了内核注释：

* 内核**不能用函数指针 `<<<>>>` 发射**（gfx926 上直接段错误），必须写发射语法。
* shared memory 按 `[行][dword]` 存、行距 32B 时，16 个线程地址间隔是 128B 的
  整数倍，**全部落在同一个 bank**（16 路冲突），GEMM 只有 3.57 TMAC/s；
  改 `[dword][行]` 后 13.07 TMAC/s。
